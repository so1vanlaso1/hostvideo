# GB10 / ASUS GX10 / DGX Spark deployment

The `arm-gb10` branch adds native Linux ARM64 deployment while retaining the x86-64 CUDA 12.8/13.x paths. The earlier CUDA compatibility work is preserved separately on `cuda12-compatible`.

## Prepare the Vast instance

Select a native ARM64/aarch64 Ubuntu/Debian image with **CUDA 13.x development tools (`nvcc`)**, GPU access and an **R580-or-newer compatible host driver**. Allocate the full 128 GB shared memory and at least 150 GB storage. A driver advertising “Max CUDA 13.0” does not establish that the development toolkit is installed. Check:

```bash
uname -m        # aarch64
nvcc --version  # release 13.x
nvidia-smi
```

Vast's listed GPU memory and system RAM are views of one shared physical pool, not independent capacities. Leave room for CPU model state, decoded frames, file caching, the OS and GPU activations. The reported PCIe link alone does not describe the integrated CPU/GPU memory path.

Clone the ARM branch into a fresh checkout and runtime environment. Reuse downloaded checkpoints by placing them under the new runtime's `models/` directory; do not copy a virtual environment, compiled extensions or dependency locks from an x86 instance.

```bash
git clone --branch arm-gb10 https://github.com/so1vanlaso1/hostvideo.git
cd hostvideo
bash setup.sh --root /workspace/minimax-h3 --skip-download
```

This installs the environment and runs actual CUDA matrix, quantized-linear/ConvRot and SageAttention correctness checks before any model download. A failure stops setup and does not write a successful build marker. After those checks pass, rerun setup to download models and start ComfyUI:

```bash
bash setup.sh --root /workspace/minimax-h3
```

Setup uses Python 3.11, PyTorch 2.13.0/cu130, torchvision 0.28.0, the pinned ComfyUI revision and SageAttention 2.2.0 source revision. Comfy Kitchen 0.2.37 is compiled for the visible GPU, using `121a` on GB10. SageAttention's pinned source detects GB10 and builds its `sm_121a` kernels. Both builders use the selected CUDA toolkit. Build parallelism defaults to four jobs and two Sage extension builds; use `MAX_JOBS=2 EXT_PARALLEL=1 bash setup.sh` if compilation consumes too much memory.

## Memory and generation settings

Automatic GB10 startup selects:

| Setting | Initial value |
|---|---|
| Model loading | Estimate-based (`--disable-dynamic-vram`) |
| Reserved memory | 12 GiB |
| Pinned host memory | Disabled |
| Model profile | Existing `int8-encoder` checkpoints |
| Node-result cache | Disabled |
| Final sampling | Existing 25 steps, Turbo disabled |
| Section duration | Existing five-second inference-window ceiling |

These settings avoid forcing all models resident before memory fit is measured. Native model management can retain models that fit and unload them when needed. CPU frame buffers remain FP16, and shared model loaders still prevent checkpoint duplication across dance sections.

To increase headroom at installation:

```bash
H3_RESERVE_VRAM=16 bash setup.sh
```

Setup saves memory settings. Explicit environment values take precedence when using the service helpers. To compare dynamic loading after completing the current job:

```bash
H3_MEMORY_MODE=dynamic H3_RESERVE_VRAM=16 bash scripts/vast.sh restart
```

Restarting interrupts any active generation. `H3_MEMORY_MODE=auto` restores hardware-based selection. The reserved amount is a model-loading headroom request, not an OS-enforced allocation limit.

Start acceptance testing with the same five-second clip, references, resolution, seed and 25 steps used on the old GPU. Record wall time, sampling time, model load/free activity, CUDA peaks and system memory pressure. Telemetry marks the shared pool; **do not add process RSS and GPU allocation peaks**. Compare cold and subsequent runs separately. Only increase section duration after measuring fit and visual continuity; additional memory does not imply proportional speedup.

For previews, explicitly select Turbo with four steps. Keep final settings unchanged until a side-by-side visual comparison supports changing them.

## Optional pose screening

ARM setup does not install the optional MediaPipe CPU pose stack by default. The H3 generation pipeline, transitions and synchronized visual review work without it. To request pose dependencies, use `H3_INSTALL_POSE=1 bash setup.sh` or install `pip install -e '.[dance-quality]'` in the runtime venv. Availability and successful execution of the optional ARM64 dependencies must be verified separately before enabling pose screening.

## Verification limits

This branch is prepared and locally tested without a GB10 instance. Successful ARM CUDA compilation, actual-checkpoint memory fit, rendering speed and output quality remain target-GPU acceptance checks. Setup and startup run the required kernel preflight rather than treating the presence of a package or a selected attention flag as proof of compatibility.
